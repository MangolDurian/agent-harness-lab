# s03 复盘：TodoWrite

## 大白话讲

实习生干多步骤的活时，容易"走哪算哪"——干着干着忘了整体计划，或者跳步骤。

s03 给他一块**便利贴**（todo_write），让他接到复杂任务时先把计划列出来：①②③，每项标个状态（没开始 / 进行中 / 做完了）。开工前先标"进行中"，干完标"完成"。

但光给便利贴没用，他可能列完就忘了维护。所以 s03 还加了个**唠叨机制（nag）**：

> 如果他连续好几次调工具都不更新便利贴，harness 就在工具结果后面追一句"喂，你已经连着 N 次没更新待办了，记得维护一下"。

最妙的是 nag 的实现方式：**不改循环**。它用一个"包装函数"（wrapper 闭包）把每个工具的 `run` 包一层，在返回结果时顺手数一下、该唠叨就追加唠叨。计数器藏在闭包里，外面看不见。

## 如果我是面试官

### 第一轮：确认你懂本质

**Q1：todo 这东西，对模型的实际帮助是什么？它又不是真能执行。**

> 它的价值是把"计划"显式写进上下文，等于给模型一个外部记忆锚点。模型每次看到自己列的待办，就更不容易跑偏或漏步骤。它不执行任何东西，纯粹是"让模型自己盯着自己"。

### 第二轮：挖设计（这是重点）

**Q2：你的 nag 提醒是怎么实现的？为什么不直接改 agent_loop？**

> 我用 handler wrapper 闭包：遍历所有 handler，给非 todo 的工具包一层，在工具返回结果后把计数 +1，超过阈值就在结果字符串尾部追加提醒；todo 工具则包另一层，调用后把计数清零。计数器是闭包里的变量。不改 loop 是因为项目铁律是 core 锁死，而且这种"横切关注点"用装饰器式的包装比侵入循环更干净、更好拆。

**Q3：为什么计数器要放闭包里，而不是全局变量？**

> 放闭包里能跟"这一次组装的 handlers"绑定，作用域干净，不会污染模块全局，也方便多个 agent 各自持有独立计数。全局变量容易串。

### 第三轮：边界

**Q4：nag 把提醒追加在工具输出末尾，会不会有副作用？**

> 会。提醒文字混进了真实工具结果里，如果工具输出本身要被程序解析，提醒就是噪声。而且它每次都触发的话会很烦。所以阈值要设合理，且最好只在"确实在执行多步任务"时才唠叨。这是个体验和约束之间的权衡。

### 临场提示
这课的招牌考点就是"**nag 怎么做到不改循环**"，一定要能清楚讲出 wrapper 闭包 + 计数器清零的逻辑。
