# s01 复盘：Agent Loop

## 大白话讲

你可以把一个 agent 想象成一个**听话的实习生 + 一部对讲机**。

- 你给他一个任务。
- 他想了想，说"我要执行这条命令"（调用工具）。
- 你（harness）替他真的去把命令跑了，把结果用对讲机念回去。
- 他听到结果，接着想下一步，再说要干嘛。
- 这样一来一回，直到他说"我搞定了，不用再干活了"。

s01 学的就是这个"一来一回"的循环本身。说白了：

> 一个 `while` 循环 + 一个能执行命令的 `bash` 工具 = 一个最小的 agent。

模型负责"想"，harness 负责"做"，做完把结果塞回去让它接着想。这个循环 (`core/loop.py` 里的 `agent_loop`) 写完之后整个项目就锁死不改了，后面所有课都是在它外面叠东西。

还有两个小设计值得记：

- **handlers 字典**：工具名 → 函数的映射表。以后加工具，就往这张表里加一行，循环本身不用动。
- **max_turns 保险丝**：万一模型陷入"调工具→调工具→死循环",跑够一定轮数就强制停，防止烧钱烧到天荒地老。

## 如果我是面试官

### 第一轮：确认你懂本质

**Q1：用一句话说，agent 和普通调一次大模型 API 有什么区别？**

> 普通调 API 是"问一句答一句"，一轮就结束。agent 是把"模型输出 → 执行工具 → 结果回灌 → 模型继续"包进一个循环里，让模型能多步骤地自己推进，直到它认为任务完成才停。核心就是这个循环。

**Q2：你这个循环靠什么判断该停？**

> 看模型返回的 `finish_reason`。如果是 `tool_calls`，说明它还想调工具，继续循环；如果是 `stop` 之类，说明它不需要工具了，循环就返回退出原因。另外有个 `max_turns` 兜底，防死循环。

### 第二轮：挖设计

**Q3：你为什么把工具分发写成一个 handlers 字典，而不是一堆 if-else？**

> 为了"加一个工具只加一行"。循环里只做 `handlers.get(name)` 然后调用，工具是什么它不关心。这样 core 和具体工具解耦，后面 11 课加工具都不用碰循环代码，符合"循环不变、机制叠加"的原则。

**Q4：如果模型调了一个你没注册的工具会怎样？**

> 不会崩。`handlers.get` 拿不到就返回一句错误提示当作工具结果回灌给模型，让它自己纠正。优雅降级比直接抛异常更适合 agent 场景。

### 第三轮：拔高

**Q5：这个最小 agent 最大的风险是什么？**

> bash 工具太强，等于把一台机器的 shell 直接交给模型。所以即便是 s01，我也加了危险命令黑名单和超时。安全边界是 harness 的责任，不能指望模型自觉。

### 临场提示
被追问时往三个方向想：**循环怎么停**、**工具怎么接进来**、**出错/失控怎么兜底**。
