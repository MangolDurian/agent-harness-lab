# s08 复盘：Background Tasks

## 大白话讲

把 agent 想象成一个**只有一只手**的助手：

- 你让他装一个特别大的库（`pip install torch`），他伸手按下回车，然后就**一直举着手等**，几分钟里啥也干不了。
- 这就是 s01~s07 的样子——`loop.py` 里 `handler(**args)` 是同步调用，函数不返回，循环就卡在那。

s08 给他的新本事是：**慢活丢后台，自己腾出手干别的**。

- 慢命令加一个开关 `run_in_background=true`，命令被丢进一个"后台小弟"（daemon 线程）去跑。
- 助手立刻收到一句"任务 bg_1 已经派出去了"，马上能接着做下一件事。
- 后台小弟干完后，结果会在助手**下一次伸手用工具时**，顺手塞到那次结果的最前面带回来。

但这里有个天生的尴尬：结果是"搭便车"回来的——**助手要是不再伸手用工具，这趟车就没人坐，结果一直卡在小弟手里**。于是又补了两道保险：

- **主动查**：给助手一个 `background_status` 工具，用户问"装好了吗"，他能伸手查一下，而不是凭记忆瞎答。
- **被动兜底**：助手这一轮活干完、准备歇手时，系统替他回头看一眼——有跑完的就塞给他再跑一轮；还在跑的，最多等 10 秒看看能不能等到收尾。

一句话总结：

> 让 agent 学会"把慢活丢后台、自己接着想下一步"；核心是用 handler wrapper 把后台结果"搭便车"塞回上下文，再用「主动查 + 超时兜底」补上"没人坐车"的漏。

为什么重要？真实开发里慢命令遍地都是（装依赖、构建镜像、跑测试）。一个一遇到慢命令就僵住几分钟的 agent 是没法用的。而且"异步任务 + 结果回收"这套，正是后面 s09 多 agent 协作的雏形——把"后台线程"换成"另一个 agent"，机制是相通的。

## 如果我是面试官

### 第一轮：确认你懂本质

**Q1：s08 的核心难点到底是什么？是"开个线程跑命令"吗？**

> 开线程是最简单的部分。真正的难点是**结果怎么回到对话里**。`loop.py` 是同步阻塞的、而且不能改（项目铁律），消息又是 OpenAI 格式——每个 `tool` 消息必须跟一个 `tool_call_id` 严格配对，我没法在中间凭空插一条 assistant 消息。所以问题变成了：**在不改循环、不破坏消息配对的前提下，把一个异步产生的结果送回同步的对话流**。

**Q2：那你最后怎么把结果送回去的？**

> 用 handler wrapper 做"输出前缀注入"。所有 handler 外面包一层，每次工具调用前先 `collect()` 一下已完成的后台任务，把通知文本拼到**这次工具正常输出的前面**。模型在下一条 tool 结果里就读到了后台通知，效果等于注入，但全程没动 loop、没插非法消息。

### 第二轮：挖实现

**Q3：为了加 `run_in_background` 这个参数，你改 `tools/bash.py` 了吗？**

> 没有。`bash.py` 从 s01 就锁着，s02~s07 都依赖它。我在 agent 层 `copy.deepcopy(bash.SCHEMA)` 复制一份，给副本加 `run_in_background` 参数。wrapper 拦截这个参数：为 true 就开线程，否则正常走 `bash.run()`，并且无论哪条路都先把这个参数 `pop` 掉，免得 `bash.run()` 收到不认识的关键字报错。原始 bash 一行没动。

**Q4：后台任务的状态是好几个线程在读写，怎么保证不乱？**

> `BackgroundManager` 内部用一把 `threading.Lock`，所有对 `_tasks` 字典的读写都在锁里。后台线程跑完改 `status`/`output` 要加锁，主线程 `collect()`/`has_running()`/`running_tasks()` 读也加锁。`collect()` 还做了"取出即清除"，避免同一个完成通知被注入两次。

**Q5（陷阱题）：你给了 `background_status` 工具查状态，那已完成的任务会不会被 `background_status` 和 wrapper 的 `collect()` 重复报一遍？**

> 不会，而且这里设计得挺巧。`background_status` 也被 background wrapper 包着，调它时 wrapper 先 `collect()`——**已完成**的任务被取走、拼到输出前缀里；然后 `status()` 函数只读 `running_tasks()`，只列**还在跑**的。两边数据源天然不重叠：完成的走前缀，运行中的走函数体。模型一次调用同时看到"刚完成的"和"还在跑的"，不会重复。

### 第三轮：边界 / 一致性

**Q6：你说后台结果"搭便车"回来，那要是模型启动完后台任务，只回了句话就停了，结果不就卡住了？**

> 这正是我第一版的真实缺口。修法是 post-loop flush：`agent_loop` 退出后，REPL 主动 `collect()` 一次，有完成通知就注入一条 user 消息再跑一轮 loop。但这只能捞到"loop 退出前就已完成"的任务。对"跑完告诉我"这种任务还在跑的场景，我又加了**超时轮询**——退出时如果 `has_running()`，就最多等 10 秒、每 0.2 秒查一次，等到收尾再注入。这样"装完通知我"才真正不依赖用户再开口。

**Q7：超时定死 10 秒，`pip install torch` 明显不止 10 秒，那不白等了？**

> 是的，这是我有意留的边界，不是没想到。超过 10 秒，轮询放弃、break，通知顺延到下一次工具调用或用户消息，那时模型靠 `background_status` 还能拿到。我没做成可配置/长轮询/事件驱动，是因为这是教学项目，10 秒够演示；生产系统应该上事件驱动（任务完成主动 push），而不是主线程死等。我把这个边界明确写进了 `docs/s08-notes.md`，避免给人"已经完美解决"的错觉。

**Q8：那个 post-loop 内循环，会不会无限 flush 下去？**

> 不会，但理由要讲清楚。每轮 flush 注入的是一条 `[系统] 后台任务完成通知` 的 user 消息，模型通常只是确认一下、不会再起新的后台任务；而 `collect()` 每轮都把完成的排空。所以新完成通知会越来越少，最终 `collect()` 返回空、`break`。我没有加"轮数硬上限"，因为终止性来自"通知会被排空"这个事实，而不是来自一个魔法数字——之前注释里写"最多 flush 一轮"是错的，我已经改掉了。

**Q9：轮询那 10 秒，程序在干嘛？会不会卡住别人？**

> 在 CLI 里轮询跑在 REPL 主线程，现象是"模型答完了但还没回到 `s08 >>` 提示符"，最多卡 10 秒。在 Web 端轮询在 `_run_agent_in_thread` 子线程里，不会卡 WebSocket 的 asyncio 事件循环，但 `processing_end` 事件会延迟最多 10 秒推给前端。两边都是"用该等的时候等一下"，可接受，但我清楚它是阻塞式的。

### 第四轮：拔高，看格局

**Q10：s08 这套"异步派活 + 结果回收"，跟后面 s09 多 agent 有什么关系？**

> 结构是同构的。s08 把慢命令丢给"后台线程"，s09 是把子任务丢给"另一个 agent"——都是"派出去异步执行、过段时间把结果收回主上下文"。s08 踩过的坑 s09 还会遇到、而且更狠：结果怎么回收（s08 的输出前缀注入）、派出去的活没人收怎么办（s08 的 post-loop flush + 超时）、状态谁来存（接 s07 的持久化任务）。可以说 s08 是用"单机线程"这个最简模型，把多 agent 协作的核心难题先预演了一遍。

### 临场提示

被问住时，往这三个方向想：

- **结果怎么回来**：异步产出怎么塞回同步、不能改的对话流？（输出前缀注入）
- **没人接怎么办**：派出去的活，如果主流程不再调工具，结果会不会永远卡住？（主动查 + 超时兜底）
- **等多久、谁在等**：兜底等待是有上限的、阻塞的——超时之后会怎样，阻塞期间谁被卡？

面试时别只说"我用线程实现了后台任务"。能主动讲出"通知靠搭便车回来，所以会卡，于是我加了两道保险，但超时上限和阻塞是我刻意留的取舍"——这种"知道边界在哪、为什么留在那"的回答，才显得你真把这套东西从头想透了。
