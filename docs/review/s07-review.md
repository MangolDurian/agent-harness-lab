# s07 复盘：Task System

## 大白话讲

把前面几课的"todo"想象成一张**便利贴**：

- 写上 ①买菜 ②做饭 ③洗碗，干完一件划掉一件。
- 但这张便利贴贴在脑门上（内存里），人一走（进程退出）就没了。
- 想改一条，得把整张重写一遍（全量替换）。

s07 把便利贴升级成一块**白板 + 存档**：

- 任务有编号，能分主任务和子任务（"做饭"下挂"切菜""炒菜"）。
- 只改一条就改一条，不用整块擦掉重写（增量更新）。
- 最关键：白板内容会**拍照存到硬盘**（`data/tasks.json`），明天回来一条不丢。

一句话总结：

> 让 agent 的任务清单从"写在脑子里、关机就没"，变成"写在硬盘上、随时能捡起来"。

为什么重要？后面要做后台任务、多 agent 协作，任务就不能只活在一次对话里，得有个大家都能看、能改、关机还在的地方存着。s07 就是在搭这个"地方"。它用三个工具替代 `todo_write`：`task_create`（建，可带 parent_id 分层）、`task_update`（按 id 改）、`task_list`（按状态查）。

## 如果我是面试官

### 第一轮：确认你懂本质

**Q1：s03 已经有 todo 了，s07 为什么还要再做一套 task？直接改 todo 不行吗？**

> todo 有三个硬伤：纯内存、全量替换、扁平结构。s07 要的是持久化、增量更新、父子层级，跟 todo 的设计都冲突。我新建 `tools/task.py` 和 todo 并存而不是改 todo，是因为项目原则是"循环不变、机制叠加"，s03–s06 还依赖 todo，我不想为 s07 破坏前面的可运行性。

### 第二轮：挖实现

**Q2：任务存硬盘，怎么保证写到一半崩了文件不坏？**

> 原子写：先写 `tasks.json.tmp`，写完用 `replace` 重命名成正式文件。重命名是操作系统级原子操作，所以要么旧文件、要么完整新文件，不会有半截文件。（加分：如果多进程同时写还不够，得加锁。）

**Q3（陷阱题）：模型 update 任务要传 id，但你打印出来是 `1.1 设计schema`，模型怎么知道真实 id？**

> 这是我目前的隐患。`format()` 输出的 `1.1` 是显示序号，不是磁盘真实 id，俩可能对不上，模型容易拿序号当 id 去 update，更新错任务。改进方向是把真实 id 一起打印，比如 `#3 1.1 [ ] 设计schema`。

### 第三轮：边界 / 一致性

**Q4：文档写"出错时整体回滚"，那 update 一批改到第三条才发现非法，前两条会回滚吗？**

> 老实说不会真回滚。实现是在循环里直接改内存对象，出错只是没 `_save()` 到磁盘，但进程内存里前两条已经被改了。严格讲这不是事务回滚，文档写得不准。要真回滚得先在副本上全部校验、全合法再一次性提交。

**Q5："全局只能有一个 in_progress"这个限制在哪些入口生效？有漏的吗？**

> update 里有检查，但 create 里漏了。一次性创建两个 in_progress 会绕过约束直接存进去。应该把这个校验抽出来让 create 和 update 共用。

### 第四轮：拔高，看格局

**Q6：s07 的持久化，对后面 s08 后台任务、s09 多 agent 协作有什么意义？**

> 意义很大。任务一旦能落盘、有稳定 id，就从"一次对话里的临时状态"变成了"系统级共享状态"。后台任务可以异步更新它，多个 agent 可以读同一份清单认领任务。s07 其实是在为"任务作为多方协作的中枢"打地基，而不只是给单 agent 记笔记。

### 临场提示
被问住时往三个万能方向想：

- **存哪儿**：内存还是磁盘、崩了会不会丢、并发会不会乱。
- **怎么改**：全量还是增量、出错了状态干不干净。
- **谁来用**：现在单 agent，以后多 agent / 后台任务会不会出问题。

面试时别只背"它能持久化"，要能主动说出**坑在哪、你会怎么修**——能讲缺点的人才像真写过这套东西。
