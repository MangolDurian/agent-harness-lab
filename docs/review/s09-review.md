# s09 复盘：Agent Teams

## 大白话讲

把前面的 agent 想象成一个**单人工作室**：

- s04 的 `delegate` 像临时外包：你把一件事打包丢给外包同学，他做完把结果还给你，然后这个关系就结束了。
- s08 的 `background` 像把慢命令丢给后台机器：机器能跑，但它不是一个会读消息、会再接任务的"人"。

s09 做的事，是把单人工作室升级成一个**小团队**：

- lead 可以 `spawn` 一个队友，比如 `alice(coder)`，给她一段初始任务。
- 队友不是一次性函数调用，而是一个独立线程里的小 agent，有自己的 system prompt、工具集和消息历史。
- 队友干完当前任务后，会 `send` 消息汇报 lead，然后进入 `idle`，每秒轮询自己的 inbox。
- lead 后面再 `send` 新任务给这个空闲队友，队友会被唤醒，用干净的新上下文继续干下一件事。
- 只有收到 `__shutdown__`，队友线程才真正退出。

这里最重要的变化不是"多开了几个线程"，而是多了一个团队里的基本单位：

> 队友 = 身份 + 角色 + 独立循环 + 收件箱 + 可复用生命周期。

消息怎么走？很朴素：

- `.team/config.json` 是花名册，记录谁在团队里、角色是什么、现在是 `working` 还是 `idle`。
- `.team/inbox/*.jsonl` 是每个人的收件箱，`send()` 就是往对方的 jsonl 文件里追加一行消息。
- `read_inbox()` 是 drain-on-read：读出来就清空，避免同一条消息被处理两次。

lead 怎么知道队友干完了？沿用了 s08 的思路：

- 每次工具调用前，handler wrapper 都会顺手 drain lead 的 inbox，把队友消息拼到本次工具输出前面。
- 如果模型这一轮已经不调工具了，REPL 还会做 post-loop flush，短时间等一下正在工作的队友。
- 最后 break 前再做一次兜底 drain，补上"队友刚好在最后一拍完成"的竞态。

一句话总结：

> s09 让 agent 从"一个人做事"变成"能派出可复用队友协作"；核心不是线程，而是用花名册 + inbox + working/idle 生命周期，把多个 agent 接进同一个同步 harness。

为什么重要？真实开发任务很少是线性的：有人查资料，有人改代码，有人跑验证，有人等结果。s09 是多 agent 协作的第一块地基，但它还不是完整团队制度。它解决了"队友能存在、能通信、能复用"，还没解决"队友之间按什么协议交接、谁认领任务、不同队友如何隔离工作区"。这些正好留给 s10~s12。

## 如果我是面试官

### 第一轮：确认你懂本质

**Q1：s09 的核心难点是什么？是开多个线程跑 agent 吗？**

> 不是。开线程只是执行方式，真正的难点是**怎么让一个队友成为可管理、可通信、可复用的 agent 单位**。如果只是开线程跑一次 `agent_loop`，那其实只是异步版 delegate。s09 要多出三样东西：身份和状态（花名册）、消息入口（inbox）、生命周期（working → idle → poll inbox → working）。有了这些，lead 才能后续继续给同一个队友派活。

**Q2：s09 和 s04 的 delegate 最大区别是什么？**

> s04 的 delegate 是一次性、阻塞、返回值式的。主 agent 把任务交出去，等子 agent 跑完，拿到结果，子 agent 就消失。s09 的 teammate 是持久的、异步的、消息式的。`spawn` 后队友在线程里独立工作，完成后通过 `send` 汇报 lead，然后进入 idle，后续还能被 `send` 唤醒继续干新任务。

**Q3：s09 和 s08 的 background 又有什么关系？**

> 结构同构，但对象升级了。s08 派出去的是一个慢命令，结果是命令输出；s09 派出去的是一个 agent，结果是队友通过消息主动汇报。两者都有同一个问题：异步结果怎么回到主上下文。所以 s09 复用了 s08 的思路，用 handler wrapper 和 post-loop flush 把异步通知送回 lead。

### 第二轮：挖实现

**Q4：你怎么表示"团队"？**

> 用 `TeammateManager` 管三件事：花名册、消息总线、线程。花名册存在 `.team/config.json`，记录 lead 和所有 teammates 的 role/status；每个人有一个 `.team/inbox/{name}.jsonl` 收件箱；`_threads` 字典保存当前进程里活着的队友线程。这样磁盘负责可观察状态，内存负责正在运行的线程。

**Q5：send / broadcast 是怎么实现的？为什么用 JSONL？**

> `send(sender, to, content)` 先校验接收者存在，然后往对方 inbox 文件 append 一行 JSON：`{"from": sender, "content": content}`。`broadcast` 就是遍历花名册，对除 sender 外的人逐个 send。JSONL 的好处是追加简单、每行一条消息，天然适合队列式写入；缺点是它不是强事务队列，生产级还需要更严格的锁、ack 和重试。

**Q6：队友为什么能复用？**

> 因为 `_teammate_loop` 不是跑完一次就退出。它先用初始 prompt 跑一轮 `_run_one_task()`，完成后汇报 lead，然后进入 `idle`，每秒 `read_inbox(name)`。如果 inbox 空，就继续睡；如果收到普通消息，就把这些消息拼成一个新 user 输入，用干净上下文再跑一轮 `agent_loop`；如果收到 `__shutdown__`，才更新状态为 `stopped` 并 return。

**Q7：为什么给新任务要用干净上下文？这样不会忘记之前做过什么吗？**

> 这是一个有意取舍。干净上下文能避免队友把上一个任务的细节、工具输出和错误路径带进新任务，降低串味。代价是队友不会天然记住完整历史，只能靠文件系统、任务描述和 lead 的消息提供上下文。对这个教学阶段来说，"可复用线程 + 干净任务上下文"比"长记忆队友"更容易理解，也更不容易爆上下文。

### 第三轮：边界 / 一致性

**Q8：队友完成后，lead 一定能马上看到吗？**

> 不一定"瞬间"，但 harness 做了三层兜底。第一层是工具调用前的 wrapper：只要 lead 下一次调工具，就会把 lead inbox 拼到工具输出前面。第二层是 post-loop flush：`agent_loop` 结束后，如果还有后台任务或 working 队友，就最多等 15 秒轮询消息。第三层是 break 前 final flush：补上队友刚好在检查和退出之间完成的竞态。超过等待窗口的结果，会顺延到下一次工具调用或用户交互。

**Q9：第一版有什么坑？你是怎么修的？**

> 第一版有两个关键坑。第一个是队友其实不持久：跑完一次 `agent_loop` 就退出，`send` 给 idle 队友只是写文件，没人会读。修法是把 `_teammate_loop` 改成 working/idle/poll 循环。第二个是工作中收到 shutdown 只从 helper 返回，外层又回到 idle，出现"嘴上说退出，线程还活着"。修法是让 `_run_one_task()` 返回 bool，收到 shutdown 返回 True，外层检查后直接 return。

**Q10：这个实现里有哪些安全或防护？**

> 有三类最基本的防护：队友名不能是 `lead/system/all` 这些保留名；名字只能包含字母数字、下划线和连字符；`send()` 会校验接收者必须在花名册里，避免消息写给不存在的人。另外 inbox 输出会截断到 50000 字符，避免队友消息把上下文撑爆。

**Q11：这个系统还不适合直接拿去生产，为什么？**

> 它是教学版，边界很清楚。第一，JSONL inbox 只是简易消息队列，没有 ack、重试、优先级和死信队列。第二，花名册虽然落盘，但线程本身不能跨进程恢复，重启后 `.team/config.json` 里可能显示有人，但 `_threads` 为空。第三，队友共享同一个工作目录，容易互相覆盖文件，工作区隔离要到 s12。第四，队友之间还没有统一沟通协议，谁等谁、谁产出什么格式，需要 s10 补。

### 第四轮：拔高，看格局

**Q12：为什么说 s09 还不是完整的"多 agent 系统"？**

> 因为它只解决了"多个 agent 能同时存在并通信"，还没解决"多个 agent 如何有秩序地协作"。真正的多 agent 系统至少还要有协议、任务分配、冲突处理、状态恢复、权限隔离和观测。s09 更像把团队成员召唤出来并给他们电话线；s10 才开始规定电话里怎么说，s11 让队友自己看板认领，s12 再让每个人有独立工作区。

**Q13：如果让你继续改进 s09，你会先改哪里？**

> 我会按风险顺序来：先让 `.team` 状态和线程状态一致，比如启动时清理 stale teammates，或者把 stopped/idle 的语义写清楚；再把 JSONL inbox 抽成更明确的消息队列接口；然后补协议字段，比如 `type/task_id/status/summary/artifacts`，避免队友只发自然语言；最后做 worktree 隔离，防止多个队友同时写同一个文件。

**Q14：这套设计最值得讲给面试官的取舍是什么？**

> 最值得讲的是：我没有改 `core/loop.py`，而是在外层叠机制。队友、后台通知、任务追踪都通过工具和 wrapper 接进同一个固定循环。这说明我理解 agent harness 的边界：核心 loop 保持稳定，新增能力靠工具、状态管理和回调扩展。代价是有些异步通知只能"搭便车"或靠 post-loop flush，但这是在教学约束下合理的取舍。

### 临场提示

被问住时，往这三个方向想：

- **队友怎么活着**：不是一次函数调用，而是 working/idle/poll inbox 的生命周期。
- **消息怎么回来**：队友结果先到 lead inbox，再靠 wrapper/post-loop/final flush 注入主上下文。
- **边界在哪里**：没有协议、没有工作区隔离、线程不能跨进程恢复，JSONL 只是教学队列。

面试时别只说"我实现了多 agent 协作"。更好的说法是：**我实现了多 agent 协作的最小 harness：身份、消息、生命周期、结果回收都有了；协议、自治和隔离还没做，分别留给后续阶段。** 这样既有亮点，也知道边界，听起来才像真的搭过一遍。
