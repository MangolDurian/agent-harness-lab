# s06 复盘：Context Compact

## 大白话讲

实习生干得越久，对话历史越长，桌上堆的纸越多，迟早把桌子（上下文窗口）堆满。

s06 教他**学会清桌子**，而且分三档力度：

1. **micro_compact（随手收）**：旧的工具输出（比如几轮前读的文件全文）不重要了，就换成一张小纸条"[已压缩：前100字…]"。每轮自动做，静悄悄的。
2. **auto_compact（大扫除）**：当估算 token 超过阈值，就把更早的一整段对话交给模型自己写个摘要，用一小段摘要替换掉原来一大坨。
3. **compact 工具（手动喊一声）**：模型自己觉得乱了，可以主动调 `compact` 触发大扫除。

最关键的还是那句铁律：

> `core/loop.py` 一行不改。压缩是怎么塞进去的？靠 `on_tool_call` 这个回调钩子 + 闭包持有 messages 引用，在每次工具调用后原地修改 messages。

还有个细节体现了对 API 格式的理解：摘要替换时用"user + assistant"一对消息，而不是单条 system，因为 OpenAI 要求角色交替；万一分割点正好落在 assistant 上，还插一条 bridge 消息维持交替。

## 如果我是面试官

### 第一轮：确认你懂本质

**Q1：为什么要做上下文压缩？不压缩会怎样？**

> 对话历史会无限增长，最终超过模型上下文窗口上限，导致请求直接失败。agent 要能长时间运行，就必须在跑的过程中持续"腾地方"。压缩就是让 agent 具备维护自己记忆空间的能力。

### 第二轮：挖设计（重点）

**Q2：你不能改循环，那压缩逻辑是怎么插进去的？**

> 利用 s01 就留好的 `on_tool_call(name, args, output)` 回调。我用闭包把 `history` 列表绑进回调，每次工具调用后回调里除了打印，还调 `compact.check_and_compact(messages)`，在 messages 上原地做压缩。下一轮 API 调用自然就读到压缩后的历史。core 一行没动。

**Q3：三层压缩为什么是这个顺序？**

> 先压最冗余、最便宜的——旧工具输出（micro），不需要调模型，纯字符串替换。token 还是超了再上 auto_compact，它要额外调一次 LLM 做摘要，成本高所以放后面。手动 compact 是给模型一个兜底的主动权。先便宜后贵，先局部后整体。

**Q4：auto_compact 替换历史时，哪些消息你绝对不能动？**

> 当前轮的 assistant 消息（带 tool_calls）和它配对的 tool 结果绝对不能删，删了 tool_call_id 配不上，API 直接报错。所以我只压缩分割点之前的旧消息，分割点之后原样保留。

### 第三轮：边界 / 风险

**Q5：摘要替换会不会丢信息？**

> 会，这是设计上的取舍。早期真实对话被一段摘要顶替，细节就没了。所以摘要 prompt 要重点保留"用户原始意图、关键操作结果、重要决策"。能接受一定信息损失，换取 agent 能一直跑下去。

**Q6：你的 token 估算用字符数除以 4，靠谱吗？**

> 不精确，中英混合偏差不小。但它只是用来判断"该不该压了"，不需要精确值。要精确得引 tokenizer 依赖，不值当。粗估够用，这是工程上的够用即可。

### 临场提示
死磕点是"**不改循环怎么实现压缩**（on_tool_call + 闭包）"和"**哪些消息不能删**（当前轮 tool_calls 配对）"。
