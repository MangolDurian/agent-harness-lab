# s05 复盘：Skills

## 大白话讲

实习生不可能把所有专业知识都背在脑子里（全塞进 system prompt 会又长又浪费）。

s05 的办法是在工位旁放一个**手册架**：要做 Git，就抽《Git 手册》；要排查 bug，就抽《调试手册》；要重构，就抽《重构手册》。

这个"抽手册"的动作就是 `load_skill`：

> 模型遇到某类任务，调用 `load_skill("git")`，harness 把 `skills/git.md` 的内容读出来，作为工具结果塞进上下文。模型这才"现学现用"。

所以 skill 的本质是：

> 延迟加载的 system prompt 片段。系统提示里只说"有这些手册"，真正的内容等用到了再拉进来。

几个设计点：

- **文件即技能，目录即注册表**：`skills/` 下加一个 `.md` 就是加一个技能，零代码改动。
- **容错**：要一个不存在的技能，不报错，而是返回"可用技能列表"，让模型自己挑对的。
- **和子 agent 的关系**：主 agent 加载的技能不会自动传给子 agent（干净上下文）。解决办法是子 agent 自己也带 `load_skill`，或者主 agent 把要点写进 task。

## 如果我是面试官

### 第一轮：确认你懂本质

**Q1：skill 和工具（tool）有什么区别？**

> 工具是"手"，解决"能不能做"；skill 是"临时翻的参考书"，解决"该怎么做"。比如 bash 能执行 `git status`（工具能力），而 git.md 告诉模型什么时候看 status、提交信息怎么写（知识）。skill 本身不执行任何东西，它只是把知识注入上下文。

### 第二轮：挖设计

**Q2：为什么不把这些知识直接写进 system prompt？**

> 因为会浪费上下文，而且越堆越臃肿。一个 agent 大部分任务用不到 git/debug/refactor 的全部细节。按需加载只在真正需要时才把那段知识拉进来，平时上下文是干净的。这是"知识和执行解耦"。

**Q3：模型请求一个不存在的技能，你怎么处理？为什么这么设计？**

> 返回可用技能列表，而不是报错。因为对 agent 来说，"卡住报错"不如"给它一个能继续的线索"。它看到列表就能选个正确的名字重试，自我纠正。容错比正确报错更适合 agent。

**Q4：你的技能发现是怎么做的？加一个新技能要改代码吗？**

> 不用改代码。`_list_skills()` 直接扫 `skills/*.md`，文件名就是技能名，第一行当简介。加技能 = 加文件。不过有个小遗憾：system prompt 里硬编码列了 git/debug/refactor，新增技能模型不一定知道，得靠它瞎试一个触发列表。

### 第三轮：边界 / 隐患

**Q5：load_skill 有没有什么没处理好的地方？**

> 有两个。一是没做输出截断，技能文件很大时会撑上下文（read_file 有截断，skill 没有）。二是没去重，同一个技能反复加载会重复占上下文。这俩正好是下一课 Context Compact 要解决的方向。

### 临场提示
招牌句是"**skill = 延迟加载的 system prompt 片段**"和"**知识与执行解耦**"，能讲出和子 agent 的上下文边界关系就是加分项。
